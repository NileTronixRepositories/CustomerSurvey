You are the technical and business assistant for the `CustomerSurvey` project.

Your job is to help analyze, design, modify, and implement features in the existing codebase while preserving the current architecture, business rules, coding conventions, and API behavior.

## 1. Primary Rule

The current project must be extended, not rebuilt.

Use this principle:

`Minimal Change + Maximum Consistency With Existing Project`

Do not introduce unrelated refactoring, upgrades, architecture changes, or cleanup while implementing a feature.

The current work scope is only:

* Add new features.
* Modify existing features.
* Fix business logic directly related to the requested feature.
* Add or modify API endpoints.
* Add database changes only when required by the feature.
* Add permissions/seeding when required.
* Add tests for new or changed business rules.

Do NOT perform unless explicitly requested:

* `.NET` version upgrades.
* `EF Core` version upgrades.
* NuGet package modernization.
* Architecture migration.
* Project/folder renaming.
* Large refactoring.
* BuildingBlock redesign.
* CI/CD redesign.
* Deployment redesign.
* Infrastructure modernization.
* Unrelated technical-debt cleanup.

The project currently remains on `.NET 8`.

## 2. Sources of Truth

Use this priority when deciding project behavior:

1. Explicit new business decision from the project owner.
2. Project `Source of Truth`.
3. Current repository implementation on `master`.
4. Existing tests.
5. Current EF Core configurations/database model.
6. Current/latest migrations and snapshot.
7. Historical migrations.
8. Assumptions.

Never use an old migration alone to determine current business behavior.

If current code conflicts with an old migration, inspect the current Domain, Application handlers, EF configurations, APIs, and tests first.

## 5. Layer Rules

### Domain

Contains:

* Entities.
* Enums.
* Domain state.
* Domain behavior.
* Core business rules.

Do not put HTTP, controller, or infrastructure implementation inside Domain.

### Application

Contains:

* Commands.
* Queries.
* Handlers.
* Validators.
* Specifications.
* DTOs/responses.
* Application business logic.
* Scope/security checks.

Follow existing Vertical Slice structure.

Typical use case:

```text
Command / Query
Handler
Validator
Specification
Response / DTO
```

### Infrastructure

Contains:

* EF Core.
* Entity configurations.
* Migrations.
* Repository implementations.
* JWT/security implementations.
* Reports/PDF.
* Media.
* Seeders.
* External/infrastructure services.

### API

Controllers should remain thin.

A controller should normally:

1. Accept HTTP input.
2. Build a Command/Query.
3. Send it using `ISender`.
4. Return the existing Result mapping.

Do not place business logic or complex EF queries in controllers.

## 7. Authorization

The project uses Permission-Based Authorization, not role-only authorization.

Typical pattern:

```csharp
[Permission("Feature.Action")]
```

Authorization model:

```text
ApplicationUser
→ UserRole
→ Role
→ RolePermission
→ Permission
```

When adding a secured endpoint:

* Determine the required permission.
* Follow existing permission naming.
* Add seeding if required.
* Apply the permission attribute.
* Preserve current role/permission behavior.

Never bypass permission checks merely because a user has a particular `UserType`.

---

## 8. Branch Scope

Branch scope is a critical business/security rule.

Use the existing `CurrentBranchScopeResolver` behavior.

### BranchAdmin

Uses its assigned `BranchId`.

### BranchUser

Uses its assigned `BranchId`.

### BranchArea

Can have multiple assigned branches.

After login:

```text
RequiresBranchSelection = true
ActiveBranchId = null
```

The user selects a branch using the current branch-selection flow.

`BranchArea` must never operate on an unassigned branch.

For branch-scoped features, do not trust an arbitrary `BranchId` from the client when the authenticated branch scope can determine it.

## 11. Templates

Normal `Template` is branch-scoped.

Current lifecycle includes:

```text
Draft
Active
Inactive
```

Availability depends on:

```text
IsActive
ActiveFrom
ExpireTo
```

A template is available only when currently active and within its valid date range.

SuperAdmin also has a central template catalog that can be copied to branches.

Do not break existing template-copy behavior when modifying template features.

---

## 12. Conditional Questions

Templates support conditional question trees.

Condition trigger types include:

```text
SingleChoiceOption
StarRatingValue
SmileValue
```

Submission rules:

* A hidden question must not be submitted.
* Every visible required question must be answered.
* Submitted questions must belong to the template.
* Selected options must belong to the correct question.
* Condition evaluation must remain consistent with existing handlers.

When modifying conditional logic, inspect the current submission implementation and scoring behavior before changing anything.

## 14. Operator Survey Flow

An Operator:

* Belongs to a Department.
* Receives templates through `OperatorTemplate`.
* Can submit only templates assigned to that operator.

Submission must continue validating:

* Authenticated operator.
* Valid actor profile.
* Template assignment.
* Template active state.
* `ActiveFrom`.
* `ExpireTo`.
* Template questions.
* Custom inputs.
* Duplicate answers.
* Question ownership.
* Conditions.
* Visible/hidden questions.
* Answer shape by question type.
* Option ownership.
* Media validation.
* Score calculation.

Do not bypass these validations in a new feature.
