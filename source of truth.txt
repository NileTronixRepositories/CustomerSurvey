# CustomerSurvey — Source of Truth

## 1. Project Identity

اسم المشروع:

`CustomerSurvey`

نوع المشروع:

`Enterprise Customer Survey & Customer Experience Management Platform`

المشروع عبارة عن منصة لإدارة استبيانات رضا العملاء على مستوى مؤسسة تحتوي على عدة فروع ومستخدمين وأقسام وموظفين، مع دعم الاستبيانات الداخلية بواسطة `Operator` والاستبيانات العامة `Anonymous/Public Surveys`.

المشروع Backend مبني باستخدام:

* `.NET 8`
* `ASP.NET Core Web API`
* `Entity Framework Core`
* `SQL Server`
* `Clean Architecture`
* `CQRS`
* `Vertical Slice Architecture`
* `MediatR`
* `Specification Pattern`
* `Repository Pattern`
* `Unit of Work`
* `FluentValidation`
* `JWT Authentication`
* `Permission-Based Authorization`
* `xUnit`

---

# 2. Current Development Scope

المرحلة الحالية والقادمة تركز فقط على:

* إضافة Features جديدة.
* تعديل Features موجودة.
* إصلاح Business Logic متعلق مباشرة بالـ Feature.
* إضافة Endpoints مرتبطة بالـ Feature.
* تعديل Database Schema فقط إذا احتاجت الـ Feature ذلك.
* إضافة Permissions أو Seeding إذا احتاجت الـ Feature ذلك.
* إضافة Tests مرتبطة بالـ Feature.

خارج الـ Scope الحالي:

* تغيير `.NET Version`.
* تغيير `EF Core Version`.
* إعادة تسمية المشاريع.
* إعادة هيكلة المشروع بالكامل.
* Architecture migration.
* استبدال `CQRS` أو `MediatR`.
* تغيير الـ Building Blocks بدون ضرورة مرتبطة بالـ Feature.
* Refactoring واسع لا علاقة له بالـ Feature.
* CI/CD changes.
* Deployment redesign.
* Infrastructure modernization.

القاعدة الأساسية:

`Minimal Change + Maximum Consistency With Existing Project`

# 5. Architectural Patterns

المشروع يستخدم:

## Clean Architecture

Dependency flow:

```text
Api
 ↓
Infrastructure
 ↓
Application
 ↓
Domain
```

الـ Domain لا يعتمد على Application أو Infrastructure.

---

## CQRS

الفصل بين:

```text
Commands
Queries
```

مثال:

```text
CreateTemplateCommand
UpdateTemplateCommand
AssignQuestionsToTemplateCommand
```

و:

```text
GetTemplateDetailsQuery
GetTemplatesPaginationQuery
```

---

## Vertical Slice Architecture

الـ Use Cases منظمة حسب الـ Feature وليس حسب نوع الملف فقط.

مثال:

```text
Features/
    Templates/
        Command/
            CreateTemplate/
            UpdateTemplate/
            DeleteTemplate/

        Query/
            GetTemplateDetails/
            GetTemplatesPagination/
```

---

## Specification Pattern

يتم استخدام `Specification` من أجل:

* Filtering.
* Projection.
* Includes.
* Pagination.
* Query logic.

لا يفضل كتابة Query logic كبير مباشرة داخل Controllers.

---

## Result Pattern

Handlers ترجع `Result<T>`.

الأخطاء تحتوي عادة على:

```text
Code
Message
ErrorType
```

مثل:

```text
Validation
NotFound
Security
Conflict
```

# 10. Authorization

المشروع يستخدم:

`Permission-Based Authorization`

ولا يعتمد فقط على Roles.

مثال:

```csharp
[Permission("Templates.Create")]
```

أو:

```csharp
[Permission("Reports.ViewSystemDashboard")]
```

العلاقة:

```text
ApplicationUser
     ↓
UserRole
     ↓
Role
     ↓
RolePermission
     ↓
Permission
```

الصلاحيات يتم تحميلها عند Login وتضمينها في JWT.

أي Endpoint جديد يحتاج Authorization يجب أن يستخدم Permission مناسبة ومتوافقة مع نظام المشروع.

# 34. Conditional Tree Rules

عند Submit:

* Hidden question لا يجوز إرسال Answer لها.
* Visible question يجب أن يتم إرسال Answer لها.
* Visibility تحسب اعتمادًا على Conditions.
* يجب منع loops أو invalid condition structures قدر الإمكان.
* Conditions يجب أن تشير إلى Questions داخل نفس Template.

# 40. Survey Submission Rules

قبل قبول Operator Survey Response يجب التأكد من:

1. Current user authenticated.
2. Current user لديه Operator profile.
3. Template assigned إلى Operator.
4. Template active.
5. Template بدأ بالفعل.
6. Template لم تنتهِ صلاحيته.
7. Template يحتوي Questions.
8. Custom Inputs صحيحة.
9. لا يوجد Duplicate Answers.
10. كل Question موجودة داخل Template.
11. Conditions يتم تقييمها.
12. لا يتم الإجابة على Hidden Questions.
13. كل Visible Questions تم الإجابة عليها.
14. Answer structure يناسب QuestionType.
15. SingleChoice Option يجب أن تنتمي للسؤال.
16. Files يجب أن تمر من Media validation.
17. Score يحسب قبل حفظ Response.

# 58. Database Rules

يتم استخدام `EF Core Configurations`.

Business constraints المهمة يجب أن تكون في أكثر من مستوى عندما يكون ذلك مناسبًا:

```text
Application Validation
+
Domain Rules
+
Database Constraints / Indexes
```

مثال:

Global Question:

```text
Scope = Global
BranchId = null
```

Branch Question:

```text
Scope = Branch
BranchId != null
```

---

# 59. Migration Rule

لا يتم إنشاء Migration إلا إذا تغير Database Schema.

أي Feature لا تحتاج Schema Change لا يجب أن ينتج عنها Migration.

---

# 60. Repository Rules

يفضل استخدام:

```text
IWriteRepository<T>
IWriteReadRepository<T>
Specifications
IUnitOfWork
```

ولا يفضل إدخال direct DbContext logic داخل Handlers إلا إذا كان المشروع الحالي يستخدم ذلك لنفس السيناريو بشكل واضح.

---

# 61. Unit Of Work

أي عملية تعدل عدة Entities مرتبطة يجب أن تحفظ Transactional consistency عن طريق:

`IUnitOfWork`

ولا يتم تنفيذ `SaveChanges` عدة مرات بلا داعٍ داخل نفس Use Case.

---

# 62. Validation

يتم استخدام:

`FluentValidation`

للـ Request Validation.

أما Business Validation التي تحتاج Database state أو Actor Scope فتوضع داخل Handler أو Domain حسب طبيعتها.

---

# 63. Controller Rules

Controller يجب أن:

1. يستقبل HTTP request.
2. يحول request إلى Command / Query.
3. يرسل عن طريق `ISender`.
4. يعيد Result باستخدام الـ existing result mapping.

لا يجب وضع:

* Business calculations.
* EF Queries.
* Domain decisions.

داخل Controller.

---

# 64. Permission Rule For New Features

عند إضافة Endpoint جديد:

يتم أولًا تحديد هل يحتاج Permission.

إذا احتاج:

```text
Create Permission
↓
Seed Permission
↓
Assign Permission to required roles
↓
Use [Permission(...)]
```

Permission naming يجب أن تتبع convention الحالي:

```text
Feature.Action
```

مثال:

```text
Templates.Create
Templates.Update
Templates.ViewAll
Reports.ViewBranchReports
```

---

# 65. Error Handling

يجب استخدام Existing `Result Pattern`.

مثال:

```text
Feature.Action.EntityNotFound
Feature.Action.InvalidState
Feature.Action.NotAllowed
```

ولا يتم رمي Exceptions من أجل Business Validation العادية.

Exceptions تستخدم للأخطاء غير المتوقعة.

# 71. Feature Development Process

قبل تنفيذ أي Feature جديدة يجب تنفيذ هذه الخطوات ذهنيًا:

```text
Understand Business Requirement
        ↓
Identify Actor
        ↓
Identify Scope
        ↓
Find Existing Similar Feature
        ↓
Identify Domain Impact
        ↓
Identify Database Impact
        ↓
Define Command / Query
        ↓
Define Permissions
        ↓
Implement Handler
        ↓
Add Validator
        ↓
Add Specifications
        ↓
Expose API
        ↓
Add Migration if required
        ↓
Add Tests
```

---

# 72. Feature Modification Rule

عند تعديل Feature موجودة:

يجب أولًا تحديد:

```text
Current Behavior
```

ثم:

```text
Requested New Behavior
```

ثم تحديد الفرق فقط.

لا يتم إعادة كتابة Feature كاملة إذا كان التعديل محدودًا.

---

# 73. Backward Compatibility

أي تعديل Feature يجب أن يأخذ في الاعتبار:

* Existing Frontend.
* Existing API contracts.
* Existing permissions.
* Existing records.
* Existing reports.
* Existing migrations/data.

لا يتم تغيير Request/Response contracts الحالية بدون ضرورة Business واضحة.

---

# 74. Database Historical Rule

المشروع مر بتغييرات Business سابقة.

لذلك:

`Old Migration ≠ Current Business Source of Truth`

عند وجود تعارض بين Migration قديمة والكود الحالي، الأولوية في فهم Current Business تكون:

```text
Current Domain
↓
Current Application Handlers
↓
Current EF Configuration
↓
Current API
↓
Latest Migration / Snapshot
↓
Old Historical Migrations
```

---

# 75. Important Example

يوجد Migration قديم يشير إلى تصميم قديم للـ Department.

لكن الـ current Domain Entity لا تحتوي `BranchId`.

لذلك لا يجب افتراض أن Department حاليًا Branch-Scoped فقط بناءً على Migration قديمة.

# 76. Rules For AI / ChatGPT Work

عند العمل على هذا المشروع يجب دائمًا:

1. مراجعة Current Code قبل اقتراح Implementation.
2. البحث عن Feature مشابهة داخل المشروع.
3. الحفاظ على Conventions الحالية.
4. عدم إدخال Architecture جديدة بلا داعٍ.
5. عدم تحديث Versions.
6. عدم تنفيذ Refactoring واسع.
7. عدم تغيير Business Rule موجودة بدون طلب صريح.
8. التفريق بين Business Requirement وTechnical Improvement.
9. ذكر أي Technical Improvement خارج Scope كاقتراح منفصل فقط.
10. إضافة Tests عند تعديل Business Logic مهم.

```text

Handler implemented
Validator implemented
Specifications implemented
Permission added if needed
Controller endpoint added
Database configuration updated if needed
Migration added if needed
Seeder updated if needed
Tests added

```

# 78. Source Of Truth Priority

في أي نقاش مستقبلي الأولوية تكون:

```text
1. Explicit new business decision from project owner
2. This Source of Truth
3. Current master branch implementation
4. Existing tests
5. Current database configuration
6. Historical migrations
7. Assumptions
```

إذا تعارض طلب جديد صريح مع هذا الملف، فالطلب الجديد يمثل Business Decision جديدة ويجب تحديث Source of Truth بعدها.
